## Error Handling

The API must use one consistent JSON error format across endpoints.

Example:

```json
{
  "error": {
    "code": "invoice_not_payable",
    "message": "Invoice is already paid",
    "request_id": "<request-id>"
  }
}
```

The exact fields may vary, but errors should be:

- Consistent.
- Machine-readable via a stable error code.
- Human-readable via a message.
- Mapped to appropriate HTTP status codes.

Representative categories include:

- Authentication failure.
- Authorization/tenant access failure.
- Validation failure.
- Resource not found.
- Invalid state transition.
- Idempotency conflict.
- External PSP failure/timeout.
- Unexpected internal error.

Sensitive implementation details and secrets must not be exposed in API errors.

## API Keys

Authentication on all business-scoped endpoints uses `Authorization: Basic base64(key_id:key_secret)` (see `DESIGN.md` §5).
`key_id` is a non-secret public identifier stored plaintext and indexed; `key_secret` is stored only as
`HMAC-SHA256(pepper, key_secret)` with the pepper sourced from the environment. The plaintext `key_secret`
is returned once at creation/rotation time and is never retrievable afterwards.

The three key-management routes below are unauthenticated demo helpers. They accept
`application/x-www-form-urlencoded` bodies (not JSON).

### Create API Key

```http
POST /api-keys
Content-Type: application/x-www-form-urlencoded
```

Form fields:

```text
business_id=<business-uuid>
```

Success response (`201 Created`):

```json
{
  "business_id": "<business-uuid>",
  "key_id": "<public-id>",
  "key_secret": "<plaintext-secret-once>"
}
```

Errors: `404 not_found` if the business does not exist; `400 validation_error` if `business_id` is missing/invalid.

### Rotate API Key

Only the secret is regenerated; the `key_id` stays the same. The old secret stops working immediately
(no overlap window — see `DESIGN.md` §5 for the production gap).

```http
POST /api-keys/rotate
Content-Type: application/x-www-form-urlencoded
```

Form fields:

```text
key_id=<public-id>
```

Success response (`200 OK`):

```json
{
  "business_id": "<business-uuid>",
  "key_id": "<public-id>",
  "key_secret": "<new-plaintext-secret-once>"
}
```

Errors: `404 not_found` if the key is unknown or already revoked; `400 validation_error` if `key_id` is missing.

### Revoke API Key

Soft-deletes the key (`revoked_at = now()`). Further requests with it fail with `401 authentication_failed`.

```http
POST /api-keys/revoke
Content-Type: application/x-www-form-urlencoded
```

Form fields:

```text
key_id=<public-id>
```

Success response: `204 No Content` (empty body).

Errors: `404 not_found` if the key is unknown or already revoked; `400 validation_error` if `key_id` is missing.

## Create Invoice

```http
POST /invoices
```

Request:

```json
{
  "customer_id": "<customer-id>",
  "due_date": "2026-09-30",
  "line_items": [
    {
      "description": "API development",
      "quantity": 2,
      "unit_amount_cents": 15000
    },
    {
      "description": "Hosting",
      "quantity": 1,
      "unit_amount_cents": 5000
    }
  ]
}
```

The server computes:

```text
2 * 15000 + 1 * 5000 = 35000 cents
```

The server is authoritative for the total. A request field such as `total`, `total_amount`, or `total_amount_cents` must either be absent from the supported input or ignored/rejected rather than trusted.

Initial state should be defined by the state-machine policy.

## Pay Invoice

```http
POST /invoices/{invoice_id}/pay
Idempotency-Key: <unique-key>
```

Request:

```json
{
  "card_token": "tok_success"
}
```

The endpoint must:

1. Authenticate and authorize the business.
2. Validate that the invoice exists and is payable in its current state.
3. Enforce `Idempotency-Key` semantics.
4. Create or locate the corresponding payment attempt.
5. Call the mock PSP over HTTP.
6. Process the PSP result safely.
7. Update payment-attempt and invoice state consistently.
8. Return a deterministic response for repeated requests using the same idempotency key.

### Idempotency Requirements

The same authenticated business + invoice + idempotency key must identify the same logical payment operation.

Repeated identical requests must not create duplicate payment attempts or charge the same invoice multiple times through the PSP.

At minimum, the implementation should enforce a database uniqueness constraint covering the logical idempotency scope. (refer to Design.md)

The implementation must define behavior for:

- Same key + same request replayed.
- Same key + different request payload.
- Request retried after the original request completed successfully.
- Request retried while the original attempt is pending.
- Request retried after an internal failure occurred.

A strong default is to reject reuse of an idempotency key with materially different request parameters.

### Concurrency

Concurrent requests using the same idempotency key must resolve to one logical payment attempt.

Concurrent payment requests for the same invoice must not allow contradictory invoice states or multiple successful payments.

## PSP Request

The precise endpoint/path may be selected during implementation, but it must accept the card token and enough payment context to identify the payment request.

Example conceptual request:

```json
{
  "card_token": "tok_success",
  "amount_cents": 35000,
  "currency": "USD"
}
```

## Webhook Endpoints

### Register Endpoint

```http
POST /webhook-endpoints
```

Example request:

```json
{
  "url": "https://example.test/webhooks/invoices"
}
```

The response should expose the generated endpoint ID and the signing secret or a secure mechanism for retrieving it.

### List Endpoints

```http
GET /webhook-endpoints
```

### Disable/Delete Endpoint

An endpoint should be disableable or deletable so that businesses can stop delivery without direct database modification.
